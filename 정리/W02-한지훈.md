## 문제

- 배민 다국어는 2021년부터 매년 시도했지만 매년 멈춘 5년 묵은 숙제
  - 2021 스펙 정의 → 2022 시스템 연동 → 2023 작업 범위 전수 검토 → 2024 다국어 사전 어드민 → 2025 타당성 분석
  - 의지가 아니라 구조의 문제. 번역이 아니라 디자인 시스템 정의 + DB 아키텍처 개편 + 전용 어드민까지 걸린 전사 시스템 개편이라 1년 이상 걸리는 작업량이었음
  - 규모도 문제. 가게 수십만, 메뉴 수천만 개인데 매일 바뀌어서 사람이 번역하는 운영 방식으로는 따라갈 수 없음

- 막고 있던 벽은 3개

| 벽 | 내용 |
| --- | --- |
| 정의 | 배민 고유 음식 용어, 브랜드 톤을 담은 번역 기준을 어떻게 만드나 |
| 구축 | 다국어 데이터 파이프라인, DB 개편, 어드민 |
| 운영 | 매일 생성·수정되는 콘텐츠를 계속 번역·유지할 방법 |

- 2026년 초에 달라진 건 두 가지
  - FDH(Food Data Hub): 2024년 12월에 오픈한 대용량 푸드 데이터 처리 시스템. 이게 없었으면 시도 자체가 불가능했다고 함
  - LLM 번역 품질: 기대 이상이고, API 하나로 연동할 만큼 구현 난이도가 낮아짐

- 그래서 사람이 번역하는 시스템이 아니라 **LLM이 변경 이벤트마다 번역해서 쌓아두는 파이프라인**으로 풀었음

### 예시 - 두바이 쫀득 쿠키

>한국어 가게명, 메뉴명이 외국인에게 첫 번째 장벽이에요.
>
>「두바이 쫀득 쿠키」를 영어/일본어/중국어로 번역하는 첫 테스트가 17:44에 성공했어요.
>
>"처음으로 어쩌면 가능하겠다"는 생각이 든 순간이었어요.

- 단순 직역이 아니라 배민에서 쓰는 용어(예: 알뜰배달 → Saver Delivery)까지 일관되게 가야 해서 정의의 벽이 따로 존재함

## 아키텍처

### 핵심 목표는 속도

- 과거 실패의 주원인은 일정이라 리소스를 많이 쓰지 않는 쪽으로 설계
- 앱 업데이트 없이 서버 배포만으로 적용. 주문 핵심 동선부터 먼저 하고 품질은 점진적으로 개선

### 두 개의 파이프라인

- **번역 파이프라인 (FDH Translation Pipeline)**
  - 가게/메뉴 변경 → 이벤트 발행 → FDH Worker가 수신 → LLM 번역 요청 → 언어별 메타데이터로 적재
  - 사용자 요청과 무관하게 비동기로 진행
- **응답 처리 (Backend BFF)**
  - 앱 요청의 `Accept-Language` 헤더를 보고 적재된 다국어 데이터를 매핑해서 응답
- 데이터를 두 종류로 나눠서 관리
  - 동적 콘텐츠(가게/메뉴): LLM 번역 파이프라인
  - 하드코딩된 UI 문구(`장바구니에 담기` 등): i18n 정적 파일

### 정적 파일 표준화

- 주문 메인 플로우만 1,600개 이상. 배포마다 항목이 추가·삭제되고 오탈자 하나가 검수를 되돌림
- 두 레이어로 분리
  - `global`: 전사 공통 용어. 중앙 관리 (예: `global.stod` = 알뜰배달)
  - `local`: 지면/서버별 독립 문구. 개별 관리

### LLM과의 협상

프로덕션 연동은 API 한 번 호출로 끝나지 않았고, 예상 밖 응답을 하나씩 잡아가는 과정이었음

| 문제 | 해결 |
| --- | --- |
| 번역 결과에 `\n`이 그대로 노출 | 프롬프트에 개행문자는 `\n`으로 escape 하라고 명시 |
| 단건 요청은 비용·속도가 비효율 | 배열 요청 / 배열 응답으로 변경 |
| 주소 번역 시 응답 필드명을 `address`로 임의 변경 | 응답 배열 이름을 `translations`로 고정하라고 명시 |

## 가능했던 이유

- LLM만으로도, 조직만으로도 안 됐다는 게 요지. 5년간 막힌 건 기술을 빠르게 실험하고 실행하는 구조가 없었기 때문
  - 기술: FDH(물리적 토대) + LLM(번역 품질). Java/Spring 서버 개발자가 익숙한 환경에서 직접 연동
  - 조직: AI 기반 구축 TF 신설. PoC 결과 하나로 전사 목표가 바뀌고, 밤 11시 역번역 데이터도 20분 만에 의사결정. 문서 없이 시작해서 문서 없이 끝냄
- 얻은 교훈 3가지
  - 공감은 설득이 아니라 돌아가는 PoC로 만든다
  - 전부 하지 않고 "없으면 오픈이 안 되는 것"만 먼저 한다
  - LLM은 챗봇이 아니라 사람의 시간으로 불가능한 영역을 푸는 생산성 도구

## 결론

- 5년간 포기된 과제가 풀린 이유는 의지가 강해져서가 아니라 기술이 바뀌었고, 그걸 바로 실험할 구조가 같이 있었기 때문
- 범위를 "없으면 안 되는 것"으로 좁히고, 막히는 건(모델 교체, 개행, 필드명) 실행하면서 고쳐나감
- 정확도, 비용 절감액, 주문 전환율 같은 정량 평가나 후속 과제는 글에 없음. 오픈까지의 과정 중심 글

## 개인 견해

- 번역 품질을 완벽하게 만드는 게 아니라 일단 오픈 가능한 수준으로 먼저 내고 개선하는 방향이라 W01 토스 글이랑 결이 다르게 느껴짐. 토스는 신뢰할 수 있게 만드는 쪽이고 여기는 일단 돌아가게 하는 쪽
- 궁금한 점
  - 중국어/일본어 품질을 같은 LLM 역번역으로 검증했는데, 번역과 역번역이 같은 방향으로 틀리면 의미가 보존된 것처럼 보일 수 있지 않나. 이걸로 검수를 대체해도 되는지
  - 모델을 Haiku에서 Nova 2 Lite로 바꾸면서 프롬프트를 처음부터 다시 잡았다는데, 다음에 모델이 또 바뀌면 품질 회귀를 어떻게 확인하는지
  - 변경 이벤트마다 번역하면 메뉴가 매일 바뀌는 상황에서 재번역 비용이 어떻게 관리되는지 (변경 감지를 해시 같은 걸로 거르는지)
