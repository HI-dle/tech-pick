### 번역 파이프라인(FDH Translation Pipeline): 데이터 번역 및 적재 레이어

- 데이터(가게/메뉴) 변경 이벤트 발행
- FDH Worker가 이벤트를 받아 LLM에 번역 비동기 요청
	- 결과를 언어별 메타데이터로 적재
	- 사용자 요청과 무관
### 응답 처리(Backend BFF Handling): 사용자 요청 및 서비스 레이어
- Accept-Language 헤더를 분석해 적재된 다국어 데이터를 매핑해서 응답
- 서버에 하드코딩된 UI 문구(ex. 장바구니에 담기): i18n(internationalization, 다국어 처리) 정적 파일로 따로 관리
	```
	Backend 다국어 정적파일
	(ko) global.all.freedelivery=배달팁 무료
	(en) global.all.freedelivery=Free delivery
	(ja) global.all.freedelivery=送料無料
	(zh) global.all.freedelivery=免配送费
	```
	> **정적 파일 표준화**
	> - 서버에 하드코딩된 UI 문구 -> i18n 방식으로 별도 관리
	> - 주문 메인 플로우만 1,600개 넘음
	> - 한줄만 틀려도 처음부터 확인 필요 = 오탈자 하나가 전체 검수
	> 	- 두 레이어 구조로 나눔
	> 		- global: 전사 공통 용어, 중앙 관리
	> 			- global.stod=알뜰배달 → 영어 파일에서 global.stod=Saver Delivery
	> 		- local: 지면/서버별 독립 문구, 개별 관리
	> 			- local.detail.stod.info=알뜰배달은…
	>
	> **두 레이어로 나눈 이유 (내 해석, 원문에 이유 설명 없음)**
	> - 근본 차이: 일관성이 지켜져야 하는 범위
	> 	- global = 용어: 한 번 정하면 모든 화면에서 같은 번역이어야 함 (알뜰배달 → 항상 Saver Delivery)
	> 	- local = 문장: 특정 지면 맥락에 묶여 그 화면에서만 의미 있음
	>
	> | 기준 | global | local |
	> | --- | --- | --- |
	> | 담는 것 | 용어 (서비스명, 기능명) | 지면별 문장 |
	> | 변경 빈도 | 낮음 | 높음 (배포마다 추가·삭제) |
	> | 변경 영향 범위 | 전 화면 | 해당 지면만 |
	> | 관리 | 중앙 한 곳 | 지면/서버별 개별 |
	>
	> - 글의 문제와 연결
	> 	- 브랜드 톤: 배민만의 용어 · 톤 기준을 global 한 곳에서 유지
	> 	- 배포 주기: 자주 바뀌는 문구를 local로 분리 → 지면별 추가·삭제가 공통 용어에 영향 없음
	> 	- 검수: 용어를 global에 한 번만 정의 → 1,600개 안에서 같은 단어 반복 검수 불필요

- 동적으로 변하는 콘텐츠(ex. 가게/메뉴): LLM 파이프 라인으로 관리
	```
	FDH 다국어 데이터
	{
	  "menuName": "두바이 쫀득 쿠키",
	  "menuNameSource": {
		"en": "Dubai Chewy Cookies",
		"ja": "ドバイのもちもちクッキー",
		"zh": "迪拜软糯曲奇"
	  }
	}
	```

## LLM
### 시스템 프롬프트
- 첫 프롬프트
	> 당신은 음식 배달 앱에서 가게, 메뉴 정보 번역을 담당하는 영어, 일본어, 중국어 번역가입니다. 응답 포맷은 json 형태로 en, ja, zh 필드로 구성되며, 각각 하나의 문자열로 작성해 주세요.
### 응답 안정화
- 개행문자
	- 문제: 번역 결과에 `\n`이 그대로 노출
	- "문자열 내에 개행문자는 \n으로 escape 해주세요." 프롬프트 추가
- 응답 필드명
	- 문제: 주소 텍스트를 번역하자 LLM이 필드명을 `address`로 임의 변경
		- 원인: LLM이 입력 내용을 보고 필드명을 스스로 정함
	- "응답 배열의 이름은 translations로 고정해 주세요." 프롬프트 추가
### 단건 → 다건(배열) 요청
- 이유: 한 건씩 요청하면 비용과 속도 면에서 비효율
- 방식: 배열로 요청, 배열로 응답
	```
	요청
	{ "message": "[\"두바이 쫀득 쿠키\", \"아메리카노\", \"장바구니에 담기\"]" }

	응답
	{
	  "translations": [
	    { "en": "Dubai Chewy Cookie", "ja": "ドバイのもちもちクッキー", "zh": "迪拜软糯曲奇" },
	    { "en": "Americano", "ja": "アメリカーノ", "zh": "美式咖啡" },
	    { "en": "Add to Cart", "ja": "カートに入れる", "zh": "加入购物车" }
	  ]
	}
	```

## 단어
- TF(Task Force, 태스크포스)
	- 특정 과제를 위해 여러 팀에서 사람을 모아 임시로 꾸린 조직
- PoC(Proof of Concept, 개념 증명)
	- 본 개발 전, 아이디어가 실제로 동작하는지 작게 만들어 확인하는 단계
- i18n(internationalization, 국제화) 방식
	- i와 n 사이 18글자를 줄인 표기
	- 코드에 문구를 직접 쓰지 않고 키(`global.stod`)로 참조, 언어별 파일(ko, en, ja, zh)에서 값을 꺼내 쓰는 방식
	- 언어 추가 시 코드 수정 없이 파일만 추가
- Spring AI Bedrock 연동 템플릿
	- Spring AI: Spring 애플리케이션에서 LLM을 호출하기 위한 Spring 공식 프로젝트
	- Amazon Bedrock: 여러 회사의 LLM(Claude, Nova 등)을 API로 제공하는 AWS(Amazon Web Services) 관리형 서비스
	- 연동 템플릿: TF가 미리 만들어 둔 Spring AI + Bedrock 연결 기본 코드 → 바로 구현 착수 가능
- BFF(Backend For Frontend, 프론트엔드 전용 백엔드)
	- 앱 · 웹 같은 특정 클라이언트 전용으로 두는 백엔드 서버
	- 여러 내부 서비스의 데이터를 모아 해당 화면에 맞는 형태로 가공해 응답
	- 이 글: Accept-Language 헤더를 보고 언어별 번역 데이터를 매핑해 응답하는 레이어
- FDH(Food Data Hub, 푸드 데이터 허브)
	- 배민 푸드 서비스의 가게 · 메뉴 대용량 데이터를 처리하는 사내 시스템
	- 이 글: 번역 파이프라인의 Worker가 동작하고, 번역 결과(언어별 메타데이터)가 적재되는 곳
- LLM(Large Language Model, 대규모 언어 모델)
	- 대량의 텍스트로 학습해 문장 이해 · 생성을 하는 AI 모델 (Claude, Nova 등)
	- 이 글: 가게 · 메뉴 원문을 en, ja, zh로 번역하는 데 사용
