## 문제

- LLM은 공개된 지식에 대해서 답변을 잘 해주지만 회사의 내부 정책이나 컨텍스트에 대한 답변은 어려워한다.
  - 문서, 코드, 미팅 로그, 사내 메신저 등에 흩어져 있는 정보는 취합 되어 정리되지 않거나 각 정보가 유효한지 판단되어 있지 않기 때문
  - 검색의 문제로 취급해 검색을 보완했으나 검색만으로는 해당 값이 유효한지 판단이 어려움

- 그래서 사내 정보를 잘 찾는것이 아닌 LLM과 사람이 함께 신뢰할 수 있는 컨텍스트를 관리해야 한다.


- 이를 토픽(Topic) 시스템을 통해 해결하고자 함

### 예시 - 주문 타임아웃의 재시도 정책

>운영 문서에는 즉시 실패 처리한다고 적혀 있어요.
> 
>미팅에서는 idempotency key를 적용한 뒤 세 번 재시도하기로 논의했어요.
> 
>현재 코드는 두 번 재시도하도록 구현되어 있어요.


- 일반적인 정책 검색에 대해 위처럼 하나의 정책에 여러 컨텍스트가 있으면 LLM은 각 실행에 단위마다 혼란을 일으킬 수 있다.

>미팅에서 실제로 결론이 났는가?
> 
> 문서가 논의보다 먼저 작성된 것은 아닌가?
> 
> 코드의 두 번 재시도가 의도된 변경인가, 아직 반영 중인 상태인가?
> 
> 세 출처가 말하는 ‘재시도’가 정말 같은 동작을 가리키는가?


- Topic은 이 반복되는 작업을 정보의 출처와 소비자 사이의 공통 계층으로 옮기고 컨텍스트의 출처와 관계, 최신성, 충돌 상태까지 함께 관리

![한지훈_1.png](image/1%EC%A3%BC%EC%B0%A8/%ED%95%9C%EC%A7%80%ED%9B%88_1.png)

- 토픽을 통한 관리를 위해 컨텍스트마다 신뢰도 점수를 계산해 총 점수를 부여하는 방식을 떠올렸지만 잘못된 부분을 설명하지 못 함
- 그래서 토픽에서 신뢰할 수 있는 컨텍스트의 조건을 6개로 나눔

  - Granularity: 독립적으로 관리할 만한 크기와 의미를 가진 컨텍스트인가?
  - Faithfulness: 설명이나 주장을 실제 원문이 뒷받침하는가?
  - Staleness: 그 근거가 지금도 유효한가?
  - Canonicality: 서로 다른 이름이 같은 대상을 가리키지는 않는가?
  - Consistency: 여러 출처의 설명이 서로 양립할 수 있는가?
  - Coverage: 중요한 근거나 관점이 빠지지는 않았는가?

- 위 항목이 하나의 검증 모델로 처리되는 것은 아니고, 수집 단계 설계 · 규칙(해시 비교 등) · LLM(의미 해석) · 사람(애매하거나 영향이 큰 결정)으로 나눠 배치함

![한지훈_2.png](image/1%EC%A3%BC%EC%B0%A8/%ED%95%9C%EC%A7%80%ED%9B%88_2.png)


## Topic 구조

### Ingest

출처를 공통 `ContentUnit`으로 정규화하되 출처별 특성은 살린다.

- 문서: 제목 계층 기준으로 분할
- 메신저: 메시지가 아니라 스레드 단위로 요약.
  - 사내 메신저는 별도의 제약을 설정해서 스레드의 결정 상태 결정에 중점을 둠
>함수명, 에러 클래스, 파일 경로 같은 기술 식별자는 원문 그대로 보존해요.
> 
> 질문, 검토한 선택지, 최종 결과를 구분해요.
> 
> 결정된 내용과 결론이 나지 않은 내용을 명시적으로 나눠요.
> 
> 대화에서 확인되지 않은 합의를 만들어내지 않아요.
> 
> 잡담 뿐인 스레드는 억지로 컨텍스트로 만들지 않아요.
- 코드: 파서로 심볼 추출 → LLM이 semantic card 생성 → 규칙으로 재검증

### Extract
- Topic은 unit에서 개념 후보와 근거를 추출한 뒤, 후보 사이의 관계를 별도의 단계에서 만든다. 중요 원칙은 개념과 관계를 원문 근거에서 떼어내지 않는 것.

- 사내 용어 병합: 약어·별칭은 자동 병합하지 않고 `Synonym Proposal`로 사람이 승인
- 문서-코드 관계에 타입 부여
  - `supported_by` :  문서의 설명을 코드 동작이 뒷받침
  - `contradicted_by` : 문서의 설명과 코드 동작이 충돌
  - `mentions` : 같은 기능을 언급하지만 뒷받침되는지 충돌하는지를 판단하기에는 부족
- 검증 호출이 실패하거나 신뢰도가 기준보다 낮으면 관계를 만들지 않음
- 관계가 없다는 건 "무관"이 아니라 "아직 확인 못 함"

### Verify

신뢰를 점수 하나가 아니라 6개 축으로 쪼갠다.

| 축 | 질문 |
| --- | --- |
| Granularity | 적절한 단위인가 |
| Faithfulness | 원문이 주장을 뒷받침하는가 |
| Staleness | 지금도 유효한가 |
| Canonicality | 같은 대상을 중복 관리하지 않는가 |
| Consistency | 출처 간 양립 가능한가 |
| Coverage | 중요한 근거가 빠지지 않았는가 |

- 변경 감지는 content hash. 해시가 같으면 `fresh`, 다르면 의미 재검증
- Faithfulness는 NLI 방식. "정보 부족"을 정상 결과로 취급
- Coverage는 점수로 주장하지 않고 "못 읽은 영역" 신호만 노출
- 이를 통해 비용과 시간 최적화

## 충돌 처리

- 삭제하거나 승자를 정하지 않고 상태로 남김. 양쪽 주장, 인용, 링크를 같이 보존
- 코드와 문서가 다르다고 코드가 항상 정답은 아님. 문서가 목표 상태일 수 있음
- 사람은 Topic이 좁혀준 충돌·변경 후보만 검토

## 에이전트가 받는 것

- 원문 조각이 아니라 출처, 인용, 지지·충돌 관계, 상태까지 같이 받음
- 상태: `trusted` / `partly_trusted` / `disputed` / `stale_risk` / `insufficient_evidence`
- `trusted`는 "절대 옳다"가 아니라 "연결된 출처 안에서 뒷받침되고 알려진 충돌이 없다"
- API/MCP로 노출해 여러 클라이언트가 같은 상태를 공유
- 사람은 해당 정보를 상태와 이력으로 판단해 사용

## 결론

- 더 많이 찾기보다 믿을 수 있게 만드는 게 중요
- 품질 판단은 분해해서 규칙, LLM, 사람에게 나눠 배치
- 불확실성은 숨기지 말고 드러내야 함
- Coverage와 팀 고유 별칭은 아직 사람이 필요. 자동화 완성을 주장하지 않음

## 개인 견해
- 답변이나 결론을 내어주기보단 결과에 대해 신뢰도 측면의 정보를 주어 사람이 더 판단하기 쉽게 제공하는 것 같음
- 최근 사내 정책을 정리하고 있어서 관리되지 않는 정책 문서나 파일, 실제 적용된 코드를 기반으로 기준을 세워 사내 정책 웹 만들고 있긴한데 생각보다 사람이 할게 많고 정책을 가져다 쓰려고 해도 문서 정책 확인, 코드 구현 확인, 충돌시 사용자에게 직접 수정 요청등 가로 막는 게이트가 많은 느낌이 듦
- 체계나 기준을 위처럼 세우면 좀 더 효율적으로 관리가 된다고 생각함 궁금한 점은 사내 메신저를 컨텍스트로 어떻게 만드는가...스레드 안에서도 잡담하거나 누가 정책을 잘 모르면 중간에 잘못된 정보가 들어가버리는 수도 있는데...요게 좀 궁금

## 토론 포인트

- 충돌을 상태로 남기는 방식이 실무에서 리뷰 부담을 얼마나 줄일까
- `trusted`의 정의가 좁은데, 사용자가 "정답"으로 오해할 위험은 없을까
