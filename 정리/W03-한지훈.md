## 문제

- 데이터 분석엔 "지난달과 같은 기준으로 이번 달도 비교해줘" 같은 반복 요청이 많음. 사람이 이전 쿼리를 찾고, 기간을 바꾸고, 집계 기준을 다시 확인하는 일을 에이전트에게 맡기는 게 목표
- 그런데 금융권이라 제약이 큼
  - 전자금융감독규정의 망분리 요건 때문에 내부망과 인터넷 업무망이 분리돼 있고, 분석할 데이터는 내부망 밖으로 못 나감 → 에이전트가 **내부망 안에서 코드를 실행**해야 함
  - 그렇다고 내부망 전체에 접근하게 둘 수는 없음. 모델이 짠 코드가 상관없는 데이터를 읽거나 파일을 잘못 고칠 수 있고, 프롬프트로 주의를 주는 것만으로는 못 막음
  - 매번 새 환경이면 이전 코드와 집계 기준을 사용자가 다시 설명해야 함 → 작업 파일과 대화 상태를 남겨야 함

- 그래서 제목 그대로 요구사항이 두 개

| 요구 | 풀어야 할 것 |
| --- | --- |
| 실행은 격리 | 모델이 만든 코드가 허용된 폴더·통신만 쓰게, 인증정보는 못 보게 |
| 세션은 이어가기 | Pod가 바뀌어도 작업 파일과 대화 상태가 남아 있게 |

### 예시 - 월별 비교 분석

- 지난달 분석에서 만든 `compare.py`와 집계 기준이 남아 있어야 이번 달도 같은 기준으로 비교할 수 있음
- 새 대화를 열 때마다 코드를 복사하면 어느 사본이 최신인지를 사용자가 관리해야 함

### 용어 정리

| 용어 | 뜻 |
| --- | --- |
| 망분리 | 업무용 내부망과 인터넷망을 나누는 것. 금융권은 규정상 필수 |
| 하네스(harness) | 모델 응답을 보고 도구를 실행하고, 결과를 다시 모델에 넘기는 반복 프로그램. 코드 오류를 모델에 보여주고 고친 코드를 다시 돌리는 것도 하네스 몫. Claude Code 같은 코딩 에이전트 CLI가 대표적 |
| Linux namespace | 프로세스마다 보이는 파일시스템·프로세스 목록·네트워크를 따로 주는 커널 기능. 컨테이너의 기반 기술 |
| bubblewrap | namespace로 프로세스 하나를 가볍게 샌드박스에 넣는 도구. Flatpak이 내부적으로 씀 |
| Unix domain socket | IP 네트워크를 거치지 않고 같은 호스트의 프로세스끼리 통신하는 통로 |
| PV (Persistent Volume) | Pod와 별개로 유지되는 Kubernetes 저장소. Pod가 죽어도 데이터가 남음 |
| MCP | 에이전트가 외부 도구의 기능을 확인하고 호출하는 표준 인터페이스 |
| OpenResponses | 모델 응답과 도구 호출을 같은 구조로 표현하는 공개 규격 |

## 핵심 개념

- **Workspace**: 사용자마다 하나 있는 개인 작업 공간. Kubernetes Pod 하나를 만들어서 계속 재사용 (Agent나 대화마다 새로 안 만듦)
- **Agent**: 업무 지침과 사용할 도구를 설정한 에이전트 (예: 데이터 분석 Agent, 문서 작성 Agent)
- **Session**: Agent와 나누는 개별 대화 (예: 10월 분석, 11월 분석)
- 플랫폼과 하네스의 역할을 나눈 게 핵심
  - 플랫폼: 요청자 확인, 실행 환경·접근 권한 준비, 저장소 연결
  - 하네스: 모델-도구 반복 호출
  - → 하네스를 바꿔도 사용자 관리와 저장소 연결을 다시 만들 필요가 없음

## 실행은 격리

### OpenSandbox란

- AI 에이전트용 오픈소스 샌드박스 런타임 (Apache-2.0, https://github.com/opensandbox-group/OpenSandbox). 에이전트가 코드·명령 실행, 파일 관리, 브라우저 조작을 할 격리 환경을 API로 만들고 관리함
- 구성
  - Lifecycle server: 샌드박스 생성·조회·삭제·pause/resume API
  - execd: 샌드박스 안에서 명령 실행, 파일 API, 코드 인터프리터를 제공하는 데몬
  - SDK: Python, JS/TS, Java/Kotlin, C#, Go
- 런타임은 Docker(로컬)와 Kubernetes. Kubernetes에선 샌드박스 하나가 Pod 하나 → 토스는 이걸 사용자(Workspace) 단위 Pod로 씀
- 글에 나온 두 통제 기능이 OpenSandbox 기능
  - egress 정책: 도메인·IP·CIDR 단위로 나가는 통신을 허용/차단. Pod에 egress sidecar를 붙여서 처리
  - 인증 프록시 (문서상 이름은 Credential Vault): 샌드박스엔 가짜 값만 주고, egress sidecar가 나가는 HTTPS 요청 헤더에 실제 인증정보를 넣음 → 글의 "대체값 → 실제 키"
  - 나가는 HTTPS 요청을 sidecar가 가로채서 바꾸는 방식이라, 글에서 "HTTP(S) 연동에만 적용"이라고 한계를 단 이유가 여기 있음
- 역할 구분: OpenSandbox는 **Pod 단위 샌드박스 + 네트워크·인증 통제**, 그 안을 하네스 단위로 더 쪼갠 것(bubblewrap 격리, Runtime HTTP 프록시)과 세션 상태 관리는 토스가 직접 얹은 부분
- 내부 동작은 맨 아래 [[#부록 - OpenSandbox 자세히]]에 따로 정리

### 실행 구조

- Workspace 실행 환경은 오픈소스 OpenSandbox가 관리. Kubernetes에 Workspace별 Pod를 만들고 종료함

| 구성 | 위치 | 역할 |
| --- | --- | --- |
| Server | Pod 밖 | 사용자·리소스 접근 권한 확인 |
| Runner | Pod 밖 | Workspace 실행 환경 준비, Runtime에 실행 설정 전달 |
| Runtime | Pod 안 | bubblewrap으로 격리 환경을 만들고 그 안에서 하네스 실행 |

- 요청 흐름: 사용자 요청 → Server 권한 확인 → Runner 환경 준비 → Runtime이 하네스를 격리해서 실행 → 하네스가 GenAI Gateway(모델), MCP Gateway(업무 도구) 호출
- 하네스엔 업무 입력과 도구만 주고 플랫폼 DB 인증정보는 안 넘김

### VM vs namespace

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| Agent마다 VM | 게스트 커널까지 분리 | VM마다 이미지·볼륨 준비, 생성·종료를 플랫폼 실행 흐름에 연결해야 함 |
| Workspace Pod + bubblewrap (채택) | 기존 Kubernetes·OpenSandbox 구성 그대로. 환경은 Workspace 단위로 만들고, 폴더·통신은 하네스 실행 시점에 연결 | 호스트 커널 공유 → VM 수준의 커널 격리는 없음 |

### 하네스 단위 접근 제한

- **파일**: 기본 실행 파일 + Agent 작업 폴더 + 사용자가 추가로 허용한 폴더 + 현재 세션 상태 경로만 마운트
  - 다른 Agent의 작업 폴더, 다른 세션의 상태는 아예 연결 안 함. 수정할 필요 없는 참고 자료는 읽기 전용
  - 파일 쓰기 도구만 막는 게 아니라 파일시스템 수준이라 Python이나 셸로 고치려 해도 거부됨. 새 도구를 붙여도 같은 격리 환경이면 똑같이 적용
- **프로세스·네트워크**: PID namespace로 프로세스 목록 격리, 별도 network namespace라 Pod 네트워크를 직접 못 씀
- **실행 권한**: 권한을 낮춘 사용자로 실행 + Linux capability 제거로 하네스가 격리 설정을 못 바꾸게 함
- 격리 준비에 실패하면 실행 자체를 중단 (fail-closed)
- 단, 접근 제한 ≠ 결과 검증. 쓰기 허용 폴더 안에서의 잘못된 수정·삭제는 못 막고, 분석 결과가 맞는지는 따로 확인해야 함

### 통신 제한과 인증정보

- HTTP(S) 요청은 전용 Unix domain socket → Runtime HTTP 프록시로만 나감. 네트워크가 분리돼 있어서 하네스가 프록시 환경변수를 무시해도 직접 못 나감
- 통신 제한은 2단계
  - Runtime HTTP 프록시: 목적지 검사. Pod 자기 주소처럼 하네스가 접근하면 안 되는 대상 차단
  - OpenSandbox egress 정책: 밖으로 나가는 허용 목적지 지정. 환경마다 허용 목록이 달라서 환경별로 설정
- 실제 API 키를 환경변수로 주면 하네스가 실행한 코드가 읽을 수 있고, 디버깅 출력으로 로그·결과 파일에 남을 수 있음 → **대체값(placeholder) 방식**
  1. 하네스는 요청 헤더에 실제 키 대신 대체값을 넣음
  2. Runtime HTTP 프록시가 목적지를 검사하고 중계
  3. OpenSandbox 인증 프록시가 정해진 목적지로 보낼 때만 대체값을 실제 키로 교체
- 한계도 직접 적어둠
  - OpenSandbox 인증 프록시가 지원하는 HTTP(S) 연동에만 적용. 모든 CLI나 개인 구독 인증정보를 이렇게 처리하진 않음
  - 키를 숨기는 것 ≠ 권한 제한. Gateway는 모델·도구 사용 권한을, 업무 서비스는 데이터 접근 권한을 따로 확인해야 함 (문서 검색 서비스 권한과 개별 문서 읽기 권한은 다름)
  - 읽은 데이터를 허용된 서비스로 보내는 건 가능해서 이 구조만으로 반출을 전부 막진 못함

## 세션은 이어가기

### 상태 저장

- 작업 파일과 하네스 세션 상태를 PV에 저장 → Pod가 교체되거나 장애가 나도 새 Pod에 같은 볼륨을 다시 연결
- 파일로 남긴 결과는 다시 읽을 수 있지만 종료된 프로세스의 메모리는 복구 안 됨. 메모리에만 있던 중간값은 재계산
- 대화 상태는 화면의 질문·답변만으론 부족. 어떤 도구 호출에서 어떤 결과가 나왔는지, 긴 대화의 압축 요약 같은 하네스 내부 정보까지 필요

### 세션 재개 방식 변경

| | 처음 | 지금 |
| --- | --- | --- |
| 방식 | 플랫폼 대화 기록을 하네스 형식으로 변환해서 복원 | 하네스가 저장한 상태 + 세션 ID를 그대로 사용. 플랫폼은 상태 경로만 기록해뒀다가 다음 실행에 연결 |
| 문제 | 하네스 저장 형식이나 도구 호출 연결 방식이 바뀌면 변환 코드가 깨짐 | 하네스 버전이 바뀌면 기존 상태를 읽을 수 있는지는 여전히 확인 필요 |

- 저장된 상태를 못 찾으면 오류 반환. 조용히 이어가면 사용자가 이전 분석 조건이 반영됐다고 착각할 수 있어서
- 세션 재개가 해주지 않는 것: 실패 지점부터 재실행, 파일을 이전 버전으로 롤백, 외부 서비스에서 이미 처리된 작업 취소 → 백업과 중복 실행 방지는 별도 설계

### 파일 공유 정책

- 같은 Agent의 대화들은 작업 파일을 공유 (지난달 `compare.py`를 새 대화에서 바로 실행). 대화 상태는 Session마다 따로
- 새 대화에 이전 대화의 분석 조건이 자동으로 넘어가진 않음. 사용자가 조건이나 요약을 알려줘야 함
- 이전 대화를 열어도 파일은 당시 버전으로 안 돌아가고, 여러 대화가 같은 파일을 동시에 고치면 충돌 가능
- 대화마다 폴더를 나누면 충돌은 줄지만 코드 복사와 최신본 관리를 사용자가 떠안음 → 공유를 택함
- Agent 간엔 완전히 분리. 분석 Agent는 참고 문서는 읽어도 문서 Agent의 작업 파일은 못 고침

### 공통 실행 기록

- 하네스 실행 중 사용자 입력·도구 호출·결과를 OpenResponses 형식으로도 저장하고, 하네스 원본 이벤트도 같이 보관
- 기록을 용도별로 나눠 씀

| 용도 | 쓰는 기록 |
| --- | --- |
| 같은 하네스로 대화 이어가기 | 하네스 고유 상태 + 세션 ID |
| 화면에서 지난 대화 조회 | 공통 실행 기록 (하네스 재실행 없이) |
| 다른 하네스로 인계 | 공통 실행 기록 요약 + 허용된 작업 파일 → 새 세션 |

- 인계는 세션 복원이 아니라 요약을 들고 새 대화를 시작하는 것. 요약에서 빠진 내용을 확인할 수 있게 원문 기록도 보관
- 기록을 못 읽으면 요약을 만들지 않고 오류. 복원에 실패했다고 자동으로 인계로 넘어가지도 않음 (사용자가 선택)
- 조회·요약을 하네스별 저장 형식에 맞춰 만들 필요가 없어진 대신, 기록 두 종류를 관리하는 비용이 생김

## 결론

- 실행은 Workspace Pod 안에서 하네스별 bubblewrap namespace로 격리하고, 세션은 PV + 하네스 고유 상태로 이어가고, 이력 조회와 인계는 공통 실행 기록으로 처리
- 플랫폼과 하네스 역할을 나눠서 하네스를 바꿔도 플랫폼은 그대로 가게 만든 게 핵심 설계
- "이 구조가 막지 못하는 것"(커널 격리, 결과 검증, 데이터 반출, 롤백)을 섹션마다 따로 적어둔 게 특징
- 정량 수치는 없음. 다음 편에서 터미널과 팀 업무 도구 연결을 다룬다고 예고
- GenAI Gateway, MCP Gateway는 이전 글(https://toss.tech/article/ai-platform-foundation)에서 다룸

### 생명주기

1. SDK가 Lifecycle server에 생성 요청 (`POST /v1/sandboxes`). 비동기라 상태는 `GET /v1/sandboxes/{id}`로 확인
2. Runtime backend가 컨테이너(Docker) 또는 Pod(Kubernetes)를 만듦
3. 샌드박스 안에 execd를 심음
   - Docker: 서버가 execd 바이너리를 컨테이너에 복사하고 bootstrap 후 entrypoint 실행
   - Kubernetes: init container가 execd와 bootstrap 스크립트를 `emptyDir`로 복사하고, 메인 컨테이너가 그 볼륨을 마운트
   - → 사용자 이미지를 고치지 않고도 아무 이미지에나 execd를 넣는 구조
4. SDK는 endpoint 조회 API로 받은 주소(Docker는 호스트 포트, K8s는 ingress gateway)로 execd(기본 포트 44772)에 직접 붙어서 명령·파일 작업. 토큰을 설정하면 `X-EXECD-ACCESS-TOKEN` 헤더 필요

| 작업 | Python SDK |
| --- | --- |
| 생성 | `Sandbox.create(image)` (sync 버전은 `SandboxSync.create`) |
| 명령 실행 | `sandbox.commands.run(cmd)` → 결과는 `.logs.stdout` |
| 파일 쓰기 / 읽기 | `sandbox.files.write_files([...])` / `sandbox.files.read_file(path)` |
| 종료 | `sandbox.kill()` 또는 `sandbox.destroy()`. `close()`는 로컬 리소스만 정리하고 원격 샌드박스는 그대로 둠 |

### Kubernetes 리소스 (CRD)

| CRD | 역할 |
| --- | --- |
| `BatchSandbox` | 샌드박스 1개 이상을 선언적으로 생성. `replicas`, `template` 또는 `poolRef`, `expireTime`, `pause` 등 |
| `Pool` | 미리 띄워둔 warm Pod를 유지 → 할당이 "스케줄링 대기"가 아니라 "준비된 Pod 가져가기"가 됨. 여유분(`bufferMin/Max`), 전체 크기(`poolMin/Max`), 반납 시 처리(`recycleStrategy`: Delete / Restart / Noop) |
| `SandboxSnapshot` | pause/resume용 체크포인트. 노드에서 rootfs를 commit해서 레지스트리에 push |

- 저장소 자체 측정으론 100개 생성 기준 BatchSandbox 0.92초, `kubernetes-sigs/agent-sandbox` provider 23~76초 (검증 안 된 자체 수치)
- 단, `poolRef`(warm Pool)를 쓰면 `volumes`·`networkPolicy`를 같이 못 씀 → 토스처럼 PV + egress 정책을 쓰는 구성이면 warm Pool 없이 매번 Pod를 새로 띄우는 쪽일 가능성이 있음 (추정)

### egress 세부

- egress sidecar가 샌드박스 컨테이너와 network namespace를 공유. 메인 컨테이너에선 `NET_ADMIN` capability를 빼서 sidecar만 방화벽 규칙을 바꿀 수 있음

| 모드 | 동작 | 못 막는 것 |
| --- | --- | --- |
| `dns` (기본) | DNS 요청을 프록시로 받아 차단 도메인은 NXDOMAIN 응답 | IP로 직접 접속 |
| `dns+nft` | nftables로 default-deny 추가. 정적 규칙 + DNS로 알아낸 IP만 허용 | 직접 IP 접속까지 차단 |

- 규칙은 `action`(allow/deny) + `target`(FQDN, `*.` 와일드카드, IP, CIDR) + `ports`, 그리고 기본값 `defaultAction`(deny/allow)
- 운영자 전용 규칙 파일(`deny.always`, `allow.always`)이 사용자 정책보다 우선이고, 1분마다 다시 읽음 (hot reload)
- nft 규칙 설치에 실패하면 프로세스 종료 (fail-closed) → 토스 글의 "격리 준비 실패 시 실행 중단"과 같은 원칙

### Credential Vault 세부

- 원리는 **TLS MITM**. sidecar(mitmproxy 기반)가 HTTPS를 가로채고, sidecar가 만든 CA를 bootstrap이 샌드박스 신뢰 저장소(시스템·NSS·JDK)에 미리 설치해둠 → 샌드박스 안 클라이언트는 인증서 검증을 끄지 않아도 됨
- 흐름
  1. 샌드박스 안에선 가짜 값만 보임 (예: 가짜 `ANTHROPIC_API_KEY` 환경변수). 실제 키는 sidecar 메모리에만 있음
  2. 나가는 요청을 바인딩(scheme·host·port·method·path)과 비교해서 정확히 하나 일치하면
  3. 인증 헤더 주입 + `substitutions`로 path/query/header/body의 placeholder를 실제 값으로 바꿔서 upstream에 전달
  4. 일치하지 않는 요청은 손대지 않고 통과. 응답 헤더에 섞인 비밀값은 가림(redact)
- 등록은 SDK `sandbox.credential_vault.create(credentials=[...], bindings=[...])`. 바인딩의 `match`로 "이 키는 이 host·path로 갈 때만" 식으로 목적지를 좁힘
- 인증 타입: `bearer`, `basic`, `apiKey`(헤더 이름 지정), `customHeaders`, `passthrough`(헤더 주입 없이 치환만)
- 제약
  - `dns+nft` 모드 + `defaultAction=deny` 필수. Istio/Envoy 같은 서비스 메시 sidecar와는 같이 못 씀
  - K8s에서 pause하면 Pod가 지워져 vault가 비워짐 → 재등록 필요
- 토스 글의 3단계(하네스가 대체값 삽입 → Runtime 프록시 → 인증 프록시가 실제 키로 교체)에서 마지막 단계가 이것

### 격리 강도

- 샌드박스 생성 시 런타임을 고를 수 있음: runc(기본 컨테이너), gVisor, Kata Containers, Firecracker microVM. Kubernetes에선 RuntimeClass로 연결
- egress는 runc와 Kata(`kata-qemu`, `kata-clh`, `kata-fc`)에서 동작. gVisor는 netstack에 nat 테이블이 없어서 egress 미지원 → 문서는 Kata 권장
- 토스가 감수한 "호스트 커널 공유"는 같은 Pod 안 하네스끼리의 얘기. Pod 자체를 Kata로 띄우면 사용자(Workspace)끼리는 VM 수준으로 나눌 여지가 있음. 토스가 어떤 런타임을 쓰는지는 글에 없음

### 볼륨

- `host`(호스트 경로 바인드), `pvc`(K8s는 PersistentVolumeClaim, Docker는 named volume), `ossfs`(Alibaba OSS)
- 토스의 "작업 파일·세션 상태를 PV에 두고 새 Pod에 다시 연결"이 `pvc` 볼륨에 해당하는 구성으로 보임 (글엔 명시 없음)
