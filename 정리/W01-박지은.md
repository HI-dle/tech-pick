## ingest: 서로 다른 세 출처를 하나의 컨텍스트 단위로
- 추출과 검증 파이프라인을 일관되게 만들기 위한 공통 `ContentUnit` 형태로 정규화
	```
		ContentUnit 개념 단순화
		├─ source_type        # document, code, messenger
		├─ unit_type          # doc_section, messenger_thread, ...
		├─ source_uri         # 원문으로 돌아가기 위한 주소
		├─ content            # 움출하거나 요약한 본문
		├─ content_hash       # 변경 감지
		├─ created_at_src
		├─ updated_at_src
		└─ metadata           # 출처별 구조와 식별자
	```
	- 출처별 구조를 보존하는 이유: 원문이 가진 의미의 경계와 증거의 출처를 잃지 않기 위해
		- metadata, unit_type, source_uri 등
	- 문서 경로, 원문 URL, 작성 · 수정 시각도 unit에 함께 남겨 이후 검증에서 사용
#### 문서는 제목 계층 보존
- docs -> chunks
- 고정된 글자수가 아닌 제목 문서로 분할
	- 고정된 글자 수로 나누면 제목과 본문이 분리되거나, 서로 다른 주제가 하나의 청크에 섞임
	- Markdown 문서를 제목 기준으로 나누고 상위 제목의 계층을 함께 저장
	- 섹션이 너무 길 때만 제한된 크기로 추가 분할
- ex. 문장만 반환하지 않고, 그 문장이 속한 제목 계층까지 함께 유지
	```
	결제 요청 실패 처리
	└─ 타임아웃 정책
	   └─ "재시도 횟수는 세 번이다"
	```
	- 문장만 있으면: 무엇의 재시도인지 알 수 없음
	- 계층이 있으면: 결제 요청이 타임아웃으로 실패했을 때의 재시도 횟수임을 알 수 있음
#### 코드는 심볼로 나누고 동작으로 다시 묶음
- code -> semantic index
```
CodeSemanticCard
├─ subject            # 무엇에 관한 카드인가
├─ behavior           # 실제로 어떤 동작을 하는가
├─ domain_terms       # 업무에서 사용하는 표현
├─ code_terms         # 코드 식별자
├─ spans[]            # repo, file, line, symbol
└─ commit_sha         # 어느 시점의 코드인가
```
#### 사내 메신저는 스레드 단위
- internal chat -> thread-lvl-summaries
- 제약
	- 함수명, 에러 클래스, 파일 경로 같은 기술 식별자는 원문 그대로 보존해요.
	- 질문, 검토한 선택지, 최종 결과를 구분해요.
	- 결정된 내용과 결론이 나지 않은 내용을 명시적으로 나눠요.
	- 대화에서 확인되지 않은 합의를 만들어내지 않아요.
	- 잡담 뿐인 스레드는 억지로 컨텍스트로 만들지 않아요.
- 관계를 추출할 때 스레드의 결정 상태를 잃지 않는 것이 중요
- 품질을 좌우하는 수집 단계

## extract: 흩어진 정보를 개념과 관계로 연결
1. extract, deduplicate
    -  각 ContentUnit에서 개념 후보와 이를 뒷받침하는 문장을 추출해요.
2. knowledge graph 
	- concept & relation
      -  같은 unit 안에서 함께 등장한 후보를 중심으로 관계를 제안해요.
      -  표기와 의미가 가까운 후보를 찾아 중복 가능성을 계산해요.
      -  충분한 근거가 있는 후보를 대표 개념(canonical concept)으로 통합해요.
      -  문서와 코드처럼 출처가 다른 unit 사이의 연결 후보를 만들어요.
      -  관계의 종류와 근거, 판단 상태를 함께 저장해요.
> - 사내 용어
>   - 동의어를 곧바로 적용하지 않고, 관련 원문을 포함한 별칭 후보(Synonym Proposal)로 만든다.
>     - 사람이 승인하면 관리되는 별칭 관계가 되고, 거절된 후보는 다시 반복해서 제안되지 않도록 기록
> - 문서와 코드의 관계: code semantic card 사이의 관계
>   - supported_by: 문서의 설명을 코드 동작이 뒷받침해요.
>   - contradicted_by: 문서의 설명과 코드 동작이 충돌해요.
>   - mentions: 같은 기능을 언급하지만 뒷받침되는지 충돌하는지를 판단하기에는 부족해요.

## verify
- 변경되지 않은 컨텍스트는 다시 검증하지 않는다. -> 비용 최적화
  - unit의 안정적인 `식별자`와 `content hash`를 이용해 변경 범위를 좁힌다.
    - 같은 원문에서 내용이 바뀌지 않았다면 추출과 연결 결과를 재사용
    - 새로 생기거나 변경된 unit만 다시 처리
    - 원본이 삭제되면 그 원본을 참조하던 관계도 함께 정리
    > 해시가 같다는 사실을 확인하기 위해 LLM을 호출하지 않는다.
    > 
    > 먼저 규칙 기반 검사로 변경 여부와 참조 무결성을 판단하고, 실제 내용이 달라졌을 때만 의미적 검증을 수행
  > - `code anchor` 사용 
  >  - 현재 코드에서 anchor를 찾을 수 없음 → orphaned
  >  - anchor가 있고 span hash가 같음 → fresh, 의미 검증 생략
  >  - anchor가 있지만 span hash가 달라짐 → 변경된 코드로 faithfulness 재검증
1. Granularity(세분성, 낱낱의 크기): 독립적으로 관리할 만한 크기와 의미를 가진 컨텍스트인가?
	- right kind of thing to be a concept?
    - 너무 짧거나 긴 unit, 내용이 거의 없는 문서 섹션, 근거가 부족한 semantic card를 점검과 선별 단계 판별
    - 원본을 어떤 단위로 읽을지 결정하는 설계부터 시작되는 품질
2. Faithfulness(충실성): 설명이나 주장을 실제 원문이 뒷받침하는가?
	- concept supported by source?
    - NLI(Natural Language Inference(자연어 추론)) 기반 검증으로 supported, refuted, not enough information
3. Staleness(낡음, 신선하지 않음): 그 근거가 지금도 유효한가?
	- source still says so?
    - 문서의 수정 시각과 content hash, 코드의 commit과 span hash를 이용해 변경을 감지
      - 변경된 원문에서도 기존 주장이 여전히 성립할 수 있기 때문에, 변경은 의미 재검증을 시작하는 신호로 사용
4. Canonicality(정규성, 표준 여부): 서로 다른 이름이 같은 대상을 가리키지는 않는가?
	- are these the same?
    - 문자열 정규화와 embedding similarity로 중복 후보를 만들고, 근거 수와 이름의 구체성 등을 이용해 대표 개념을 선택
        - 모호한 후보에는 자동 병합 대신 사람의 승인
5. Consistency(일관성): 여러 출처의 설명이 서로 양립할 수 있는가?
	- do these agree?
    - 같은 개념을 설명하는 evidence가 둘 이상이면 출처가 다른 조합을 우선 비교
      > - consistent: 같은 내용을 설명해요.
      > - complementary: 서로 다른 부분을 설명하지만 함께 성립할 수 있어요.
      > - contradicts: 동시에 성립하기 어려운 주장을 해요.
      > - unrelated: 동일한 개념과 관련되어 있지만 직접 비교할 수 없어요.
6. Coverage(포괄성, 다룬 범위): 중요한 근거나 관점이 빠지지는 않았는가?
	- what's missing?
    - 출처별 점검, 코드 영역별 semantic card 분포, 추출 과정에서 발견한 coverage gap처럼 관찰 가능한 신호를 관리
      - overage를 완성된 하나의 점수로 주장하기보다, 어느 출처와 영역을 아직 충분히 읽지 못했는지 드러내는 방식에 가까
